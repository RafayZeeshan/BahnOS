AILog: how BahnOS was built with AI
=====================================

Prompt Operations Hackathon, Bahn's "Car Delivery Control Room" challenge, 24-25 October 2026.
Repository: github.com/RafayZeeshan/BahnOS

This log covers the whole project: every prompt we gave the coding agents, the questions they
asked us and our answers, the architecture decisions, the back and forth where we changed course,
the bugs, and what was verified. The main coding agent was Claude Code (Claude Opus 5.5), with
subagents for independent review. BahnBot itself runs on Claude Sonnet 5.5 through OpenRouter.

Sources: the seven Claude Code session transcripts for this project, the git history, the
architecture decision records in docs/decisions/, and docs/AI-LOG.md. Times are UTC. API keys that
appeared in prompts are redacted. Everything in the dataset is fictional.

1. THE PRODUCT IN ONE PARAGRAPH
-------------------------------
BahnOS is a control room for Bahn's operations team. An agent, BahnBot, watches every trip,
warns early when a travel plan looks shaky (Heads-up / Watch), gathers the facts, and brings a
person one decision with evidence for every fact: Go ahead, Change it, Take over or Not this.
It never contacts a customer, never buys anything on its own, and stops when a person must
judge. Around it: Today (only the orders that need a person), a case view, the Ops map (every
order as a lane between cities), a Risk outlook (which routes, modes, makes and pickup sites
keep causing trouble, never scoring drivers), an Answer book of driver policy that BahnBot
follows, and a Learning loop (Dream) that replays candidate rule changes on past orders and
lets a person adopt them. Stack: Next.js 16, React 19, TypeScript, Postgres via Drizzle,
Vitest, the Anthropic SDK, Motion, Geist, Leaflet and MapLibre.


2. HOW THE WORK WENT, PHASE BY PHASE
------------------------------------

Phase 0. Understanding the packet (24 Oct, morning)
  - "go through the entire repo and understand the Bahn case study for this hackathon"
  - "run the starter app" / "run it. download whatever is needed": Node, Docker and the
    starter were set up so the packet's own board, records and inbox could be seen running.

Phase 1. Planning, challenged hard (24 Oct, afternoon and evening)
  - /grill-me on BUILD-PLAN.md. Claude asked nine questions; our answers shaped the plan:
      * "Approved" became "Intervene": a person's response is an intervention, and
        interventions feed learning.
      * First "create more dummy data", then reversed: "Forget synthetic data lets only use
        the data Bahn has provided."
      * First "use a simulated clock", then reversed: "no need for simulated clock lets work
        on the dates based on the data bahn has already given us." This became the frozen
        clock (ADR-003).
      * "Dream should be self recursive improvement ... so that the agent can learn from
        already dealt cases and how they came out."
  - "check palantirs gotham see how they do it for the military": researched for
    common-operating-picture ideas.
  - "Compare this build plan with the Bahn-hackathon-brief.pdf, use /llm-council to come up
    with a solid plan to win": a five-advisor council reviewed the plan. Its verdict cut the
    "chaos button" and the simulated driver persona as spectacle, not signal.
  - Maps: "the travel assist for the driver should include google/geo maps", then "You don't
    need the Google Maps API, we need to just embed it". This led to Leaflet on OpenStreetMap
    with an "Open in Google Maps" link per leg (ADR-012), shown to both the driver and ops.
  - "for the map precision generate synthetic data": the one place synthetic data is
    allowed, a clearly labelled geo layer. Same prompt: "There should be an agent that flags
    the cases ... when the travel plan starts looking sketchy." This became Watch (ADR-008).
  - Risk: "add a risk evaluation system based on the drivers/freelancers, the dealerships,
    modes of transport". We then corrected ourselves: "we are not scoring drivers but the
    source of failures ... routes, modes, makes, dealerships ... The root cause is what the
    risk evaluation section is for." This became ADR-009: risk by source of failure, never by
    driver.
  - "go out and research what problems competitors of bahn in ... USA, UK encounter":
    a competitor research pass.
  - Dream: "A system that uses the dream RSI and harness2 concepts to run simulations ... until
    it could predict point of failures ... gets better as new data comes in ... if something
    changes ... should trigger the recursive learning." This became ADR-010 and ADR-011: one
    evaluate(policy, order, t) engine, and a policy (the "harness") that changes around a
    fixed model, with a person adopting each change.
  - UI: "use https://github.com/morluto/rea reverse engineer anything on linear.io UI to build
    the control room dashboard", plus a reference image, merged into the same plan. REA was
    installed (Node via fnm). The decision was to take Linear's interaction patterns but not
    its code, assets or look (ADR-013).
  - Tooling: the addyosmani/agent-skills pack was installed globally for Claude Code.

Phase 2. Review, odds, voice, ADRs (24 Oct, evening)
  - "can you tell me what's the plan. give me a short version": summarised.
  - "review this build plan ... and give me chances of this winning". The honest verdict: the
    plan was about twice the work the time allowed, and it was cutting case chat, which the
    brief requires. Chat moved out of the cut list.
  - "Keep the plan as is for now."
  - "use https://github.com/Abdullah12has/prometheus ... for the voice talking agents part":
    added as a sidecar plan (ADR-014). It stays Proposed: the repo has no licence, so no code
    was copied, and calls in the product are recorded, fictional transcripts.
  - "there's anthropic api key in the .env file ... use all of this plan to create ADRs":
    ADR-001 to ADR-015 written, plus an index. Only the key's name was ever read, never its
    value.
  - "Commit the working tree changes with a sensible message."

Phase 3. The autonomous build loop (24 Oct night into 25 Oct)
  - /agent-skills:build "run a develop, review, fix loop until all the adrs are fully complete
    and running and setup ... setup heartbeat".
  - Claude asked four questions before starting. Our answers: derive docs/SPEC.md and
    tasks/plan.md from the plan and ADRs; install Node 24, npm and Docker; aim for everything in
    all ADRs; accept both ANTHROPIC_API_KEY and CLAUDE_API_KEY.
  - "Approve. Docker is open and running. Start the build loop with a heartbeat."
  - The loop ran tasks T0 to T25 test-first: a failing test, then the code, the full suite,
    the typecheck, the build and one commit per task. A cron heartbeat kept it going. See
    Appendix B for the commits.
  - Two independent subagent reviews ran near the end:
      * A "tired ops person" reviewed every screen against the plan's checklist: 20 findings,
        all fixed.
      * A code reviewer read the agent, guard and decision code: 13 findings, all fixed.
        These covered races between undo and execute, colliding proposal ids, blockers cleared
        by the wrong order's check, recipients trusted from model labels, and replay reading
        the future.
  - The replay fix changed the headline result. The early "v2 catches 8 of 21 problems a day
    ahead" disappeared once replay could no longer see the future. We kept the honest
    result: nothing beats v1, and the screen shows each try.
  - Blocked: the Anthropic key returned 429 on every model. Claude refused to hand-write agent
    traces to fill the gap. Live voice was blocked on the prometheus licence. The heartbeat
    was deleted when every task was done or blocked.

Phase 4. The agent goes live (25 Oct, morning)
  - "use this: [API KEY REDACTED]" (an OpenRouter key). It was saved to the gitignored root
    .env and never committed. The client was pointed at OpenRouter's Anthropic-compatible
    endpoint. All six demo runs were recorded live. CD-420299 asked the ferry company before
    proposing anything. Go ahead ran a booking through to EXECUTED, and Ask the agent answered
    live. Claude advised rotating the key, since it had been pasted into a chat.
  - "run the app I want to see it": it ran, and the first live runs exposed an oversized
    headline (real agent text is long).
  - "what else is left for dev in the ADRs?" then "finish the rest":
      * Watch's model step was only half built (7 of 9 cards used template text), so each
        flagged order now gets one small model call writing one line and a cheap next step.
      * Long headlines keep their first sentence.
      * A fresh clone never loaded the recorded runs (setup skipped them), so `agent:load`
        was added. A fresh-clone test confirmed it.

Phase 5. Premium UI, and Sonnet 5.5 (25 Oct)
  - "recreate the entire UI ... taking Framer UI components ... right now the app looks really
    bad and theres too much text ... make sure the open router api key is configured for
    Sonnet 5.5 and not opus 5.5 ... this needs to look and feel really premium".
  - Claude asked two questions. Our answers: "Framer" means Motion (the open-source library
    behind Framer) plus a component kit in code; the screens should be glanceable, with
    details on demand.
  - Sonnet 5.5 became the default model, and all runs and Watch lines were re-recorded on it.
    One wording flaw was kept and logged (a pickup time without a time zone).
  - A new design system (ADR-016): Motion, bundled Geist fonts, light and dark tokens, one
    accent, and car photos as model illustrations. Today shows one line per order. A case
    shows the situation, then one decision card; the reasoning sits behind a click and the
    details sit in tabs.
  - The rebuild surfaced real bugs, all fixed:
      * An approval could stall when a refresh reordered decisions created in the same
        instant.
      * demo:reset kept old live answers.
      * JavaScript entrance animations hid content in background tabs.

Phase 6. BahnOS: the ops map and the answer book (25 Oct)
  - "Clone this repo: Bahn-Express/car-delivery-control-room. Take out the Ops Map ... the
    answer book ... change the name of the bot to BahnBot ... this entire thing should be
    called BahnOS ... This repo has very little actual functionality of the bot ... Ask if you
    have any questions."
  - Back and forth: that repo held only the challenge packet. The only map features Claude
    found were in two forks that looked like other teams' entries, with no licence, so it
    stopped and asked instead of copying them. Our answer pointed to our own team's repo,
    toivonenlate/OperationsHackathonPrometheus.
  - Three more questions, three answers:
      * Today stays home; the map gets its own page.
      * The map shows the snapshot, not the prototype's live simulation, which would have
        been a second, simpler bot making decisions.
      * Keep the live news and holiday feed.
  - Ported:
      * The ops map (MapLibre) with lanes, clocks, filters, inspector, handover checks,
        timeline, event log and disruption watch. It is coloured by BahnOS's own queue and
        BahnBot's decisions, not by the prototype's bot.
      * The answer book (80 driver questions, each routed: answer alone, from the records,
        ask first, or a person decides). BahnBot looks it up with a new answer_book tool, in
        the driver's own market.
  - Renamed the product to BahnOS and the agent to BahnBot on every screen and in the prompt.
    The packet's own agents keep their titles.
  - Tailwind was scoped to the ported pages, with our CSS in a lower cascade layer. The first
    tries showed grey browser buttons and an unstyled answer book; both were fixed.
  - Checked live: asked about driving on with a red warning light, BahnBot looked up the
    answer book and would not promise tow cover from a Germany-only entry. The tool was then
    made to apply the driver's market itself.
  - The six runs were re-recorded with BahnBot's prompt; five now consult the answer book.
    ADR-017 written. A fresh clone passed setup, tests and build.

Phase 7. The BahnOS repository, the risk map, this log (25 Oct, midday)
  - In a parallel session: "commit and push everything", "I created a repository on desktop
    called BahnOS ... check that the Open router API key and the Claude OAUTH token are in

  - "are there any differences from the previous working folder?": the code was identical. The

  - "add the Ops maps functionality to the Risk Outlook tab ... a secondary option": Risk

  - "Push the commit to origin main": the agent's shell had no GitHub credentials, so we

3. ARCHITECTURE DECISIONS (docs/decisions/)
-------------------------------------------
ADR-001  One agent (the Recovery agent, now BahnBot) with three triggers: Watch, On the road,
         Ask. Accepted.
ADR-002  The brief's rules are enforced in code by typed actions and a guard; the prompt only
         describes them. Accepted.
ADR-003  Time is frozen at the snapshot, 2026-10-21T09:00Z; a test scans for wall-clock
         calls. Accepted.
ADR-004  Recorded agent traces by default, live runs with an API key; traces are never
         hand-written. Accepted.
ADR-005  Build on the Next.js starter, with agent state in separate tables. Accepted.
ADR-006  Four human responses (Go ahead, Change it, Take over, Not this); "approved is not
         done" until the executor reports; a 5-second real-time undo. Accepted.
ADR-007  Every fact carries an evidence ladder: claimed, reported, observed, verified.
         Accepted.
ADR-008  Watch: a rules-only sweep first; the model only writes the warning line and the cheap
         next step for flagged orders. Accepted.
ADR-009  Risk by source of failure (route, mode, make, dealership), never by driver; k of n
         with shrinkage. Accepted.
ADR-010  One pure evaluate(policy, order, t) engine for Watch, replay and simulation; it never
         reads past t. Accepted.
ADR-011  Dream learns by changing the policy around a fixed model; held-out replay; a person
         adopts each change. Accepted.
ADR-012  Leaflet on OpenStreetMap over a labelled synthetic geo layer, with a route-strip
         fallback. Accepted.
ADR-013  A triage queue, not a board; Linear's interaction patterns, not its look. Accepted;
         its visual system is superseded by ADR-016.
ADR-014  Voice calls through a prometheus sidecar. Proposed: pending a licence for that
         repository.
ADR-015  The packet is read through an in-memory index for the agent and the engine. Accepted.
ADR-016  A premium visual system on Motion and Geist, with details on demand. Accepted.
ADR-017  The team's ops map and answer book are brought in; the product is called BahnOS and
         the agent BahnBot; the risk outlook gets a map tab. Accepted.


4. TIMES WE DID NOT TAKE THE FIRST ANSWER
-----------------------------------------
From docs/AI-LOG.md:

1. First answer: CD-420299 as "the booking failed, go to Plan B"
   Instead: "Unknown outcome, so verify with the provider first"
   Why: The data says the outcome is unknown, and rebooking risks a double booking. The guard now refuses a booking proposal while that blocker is open.

2. First answer: A chaos button and a simulated driver persona
   Instead: Cut
   Why: Council review: spectacle, not signal. Recorded replies do the job.

3. First answer: Synthetic orders to show more cases
   Instead: Dropped; only the geo layer is synthetic, and it's labelled
   Why: The brief says to keep the world as given.

4. First answer: A single "Approve" button
   Instead: Go ahead / Change it / Take over / Not this, with reasons
   Why: Approve-only loses why people disagree, so nothing can be learned from it.

5. First answer: The plan's CD-420603 example: "check-in closes in 6 h 40 m; the driver can arrive in about 5 h"
   Instead: "Check-in closes in 3 h 0 m", with the driver's own words shown as a claim
   Why: Checking against the data, those numbers weren't in the packet, and there's no verified driver position at all. Plan corrected.

6. First answer: The plan's risk numbers: 24 mishap orders, Volvo 5 of 8, DE→FI 4 of 9
   Instead: 21 orders, Volvo 3 of 5, DE→FI 3 of 9 (2 of 9 counting only route causes)
   Why: Counted from the data. The UI only ever shows what the data gives.

7. First answer: A test expecting FR→FI "3 of 3"
   Instead: 2 of 3
   Why: Our own rule (ADR-009) says a route answers only for route and mode problems. The third order's problem was something else. The test was wrong, not the code.

8. First answer: "Train legs: 2 of 5 had a problem"
   Instead: 0 of 5
   Why: A sold-out *ferry* was being counted against trains on the same order. Caught by reading the output, then fixed so a mode problem only counts against its own mode.

9. First answer: Watch flagging CD-420449's "26 h old quote"
   Instead: Not flagged
   Why: The first fix (skip booked legs) still flagged it. The data showed the leftover quote was an unpurchased alternative, so the rule is now: stale quotes only count when nothing is booked.

10. First answer: Replay of v1 showing almost no lead time, read as "Dream doesn't work"
   Instead: Kept as the honest baseline, and tried the policy lesson it points to: also watch orders on risky sources
   Why: Watch's signals are the same records that define a mishap, so v1 can't see ahead. See row 15 for what happened to the lesson.

11. First answer: Forcing a v3 policy because the plan's definition of done said "v1 → v2 → v3"
   Instead: Let the stop rule decide
   Why: The stop rule is part of the design. In the end there is no v2 either (row 15).

12. First answer: Hand-writing agent traces when the API key returned 429 on every model
   Instead: Refused, and waited for a working key. The six traces were then recorded live through OpenRouter
   Why: ADR-004: recorded mode replays real runs. Fake traces would be dishonest here and in this log.

13. First answer: Committing macOS-generated audio for the recorded calls
   Instead: The browser's own speech engine reads the transcript
   Why: Licensing of system-voice recordings in a public repo is unclear, and the files wouldn't play the same on a judge's machine.

14. First answer: Copying prometheus's voice code into the repo
   Instead: Not copied
   Why: The repository has no licence. ADR-014 stays "Proposed" until the owner adds one.

15. First answer: "v2 catches 8 of 21 past problems a median 24 h ahead", shown on the screen and in the README
   Instead: Withdrawn: scored honestly, nothing beats v1
   Why: The code-review subagent found that replay read facts from after each checkpoint: an order's later travel, final booking statuses, and other orders' later problems. Fixed with tests, the gain vanished; every candidate catches the same 2 of 21. We kept the honest "nothing to decide" result and the screen shows each try.

Later in the project:

16. First answer: Port the ops map from the forks Claude found in the Bahn-Express network
   Instead: Stopped and asked; used our own team's repository
   Why: Those forks were other teams' entries with no licence.

17. First answer: Port the prototype's live simulation and its suggestion rules with the map
   Instead: The map shows the snapshot, coloured by BahnOS's own queue and BahnBot
   Why: Two sources of decisions would contradict each other, and the frozen clock (ADR-003)
        would break.

18. First answer: Run `demo:reset` to load the re-recorded runs
   Instead: Load only the recordings, and remove only the agent's own test question
   Why: Reset would have deleted live questions a teammate had just asked BahnBot.

19. First answer: Rewrite the 2,500-line map in our own CSS
   Instead: Keep its Tailwind, scoped to two folders, with our styles in a lower cascade layer
   Why: Less drift from the team's design, and no other page changes.


5. BUGS THE AGENTS MADE OR FOUND, AND HOW THEY WERE CAUGHT
---------------------------------------------------------
- A stylesheet was emptied by its own script (opened for writing before reading). Caught in
  the browser; rewritten.
- The dev server ran stale code, so v2 showed v1's score. Caught by running the same function
  outside Next.
- A `route` field name collided in the case API and crashed the page. Renamed `geo`.
- Server code was pulled into the browser bundle (node:fs). Split into lib/geo/types.ts.
- New CSS class names clashed with the starter's. Fixed with prefixes and renames.
- From the code review: undo could lose a race with execute; proposal ids collided across
  runs; a provider check for another order could clear a blocker; "never contact a customer"
  trusted a model-filled label; replay read facts from after each checkpoint.
- A fresh clone never loaded the recorded runs. Found while adding Watch lines; caught by a
  fresh-clone test.
- An approval could stall at "Approved" after a refresh reordered decisions created in the
  same instant. Found by clicking Go ahead in the new UI; fixed with stable ordering and a
  real-time execute fallback, plus tests.
- demo:reset kept old live answers from another model. Fixed; the test is scoped to its own
  order so it never deletes real answers.
- JavaScript entrance animations left content invisible in a background tab. Moved to CSS.
- The undo toast was trapped mid-card by an animated ancestor. Moved to a portal.
- Ported map: grey browser-default buttons (no Tailwind base reset), an unstyled answer book
  (the dev server had cached the stylesheet from before that folder existed), sideways scroll
  on phones (no grid column at small widths), and the packet's own agents labelled "BahnBot".
  All fixed.
- Found and left as an open item: each "Ask BahnBot" that ends in a proposal adds another
  open proposal for the same order.


6. WHAT WAS CHECKED, AND HOW
---------------------------
- Test-first throughout. The Vitest suite grew from 0 to 253 tests: the guard, the decision
  state machine with concurrent requests, replay leakage, Watch, risk, the answer book lookup
  and markets, ops map needs, the risk map, and a scan that keeps wall-clock time out of agent
  and UI code.
- Typecheck and production build after each task.
- Fresh-clone tests, on separate ports with their own containers, at hand-in, after the setup
  fix, and after the ops map port. Each time: install, setup, all tests, build.
- Every screen opened in a browser in light, dark and phone sizes after each UI change.
- Live checks:
  * CD-420299 verifies with the provider before proposing.
  * Go ahead runs to EXECUTED.
  * Ask BahnBot answers.
  * BahnBot consults the answer book and respects market rules.
- Secrets: keys live only in gitignored .env files; we checked the git history for keys before
  pushing.
- Every number on the main screens and in the README was checked against the packet.
